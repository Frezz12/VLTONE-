# Ревью хоста плагинов — 19 сентября 2026

## Итог и границы проверки

Найдена и исправлена воспроизводимая причина симптома «звук проходит мимо Waves RCompressor»: хост включал неподключённый вход сайдчейна VST3. На установленном RCompressor Stereo подтверждена обработка тестового сигнала после исправления, в том числе offline.

Проверены общая цепочка PluginNode/AudioGraph и адаптеры поддерживаемых внешних форматов: VST 1.x/2.x, VST3, CLAP, Audio Units. Для Windows собраны и запущены тесты VST2/VST3/CLAP. AU просмотрен статически; выполнение AU возможно только на macOS и здесь не проверено. Это ревью хоста, не сертификация всех установленных сторонних плагинов и не аудит их закрытого исходного кода. Внутренние эффекты затронуты общими тестами графа и рендера; AAX/LV2 в этой сборке не реализованы.

Setup не собирался, установленное приложение не заменялось. Сторонние плагины, лицензии и пользовательский проект не редактировались. Использован подход ponytail: исправления в существующих адаптерах, без новых зависимостей и отдельной архитектуры обработки.

## Исправленные проблемы

### P1 — RCompressor не сжимает сигнал без внешнего сайдчейна

`Vst3Instance::allocateAndActivateBuses` всегда активировал входную шину 1. Когда пользователь не подключал сайдчейн, в неё подавалась тишина. RCompressor выбирает внешний детектор по состоянию активации этой шины: основной сигнал проходит, но детектор не видит сигнал, который должен запускать компрессию.

Теперь AudioGraph передаёт факт подключения ребра Sidechain через PluginNode в PluginProcessInfo. Дополнительный вход VST3 активируется только при реальном подключении. Подключённый источник, временно выдающий тишину, остаётся подключённым. Изменение соединения инвалидирует подготовку плагина; подключение и отключение проверены как для realtime, так и для offline. Буферы объявленных шин остаются корректными, даже если шина неактивна.

Файлы: `engine/Graph/AudioGraph.cpp`, `engine/Graph/Node.hpp`, `plugins/Host/PluginNode.cpp/.hpp`, `plugins/Host/PluginTypes.hpp`, `plugins/Vst3/Vst3Instance.cpp`.

### P1 — Падение Waves при завершении процесса на Windows

После успешной обработки и удаления экземпляра диагностический процесс иногда завершался с access violation `0xc0000005`. Отладчик показал цепочку `ExitProcess → LdrShutdownProcess → WaveShell → InnerProcessDictionary_x64!ReleaseDictionaryItemRefCon → RtlEnterCriticalSection`.

Кэш VST3-модулей намеренно никогда не уничтожался, поэтому нормальные `factory->release() / ExitDll() / FreeLibrary()` пропускались. На выходе Waves обращался к уже разобранным зависимостям. На Windows кэш теперь освобождается на этапе CRT shutdown, до системного DLL detach. Глобальный host context создаётся раньше кэша, чтобы пережить освобождение фабрик. Во время работы модули по-прежнему кэшируются, экземпляры сохраняют собственные shared_ptr: это не выгрузка после каждой вставки. Политика macOS/Linux не менялась.

В Windows-фикстуру добавлена проверка вызова ExitDll до разрушения DLL. После исправления девять последовательных запусков настоящего Waves завершились с кодом 0: по три realtime, offline и контрольных с активным пустым сайдчейном. Во всех случаях RMS соответствовали таблице ниже, экземпляр корректно удалялся до выхода. Исправление не гарантирует безопасную выгрузку любого дефектного стороннего DLL.

Файл: `plugins/Vst3/Vst3Module.cpp`.

### P1 — Небезопасный порядок разрушения экземпляра VST3

COM-ссылки на processor/controller могли освобождаться уже после разрушения объектов хоста, которыми они пользуются. Кэшированный unattached editor view также сохранялся до `controller->terminate()`. При неуспешном `component->initialize()` вызывался `terminate()`, хотя инициализация не состоялась.

Теперь listener отключается, все views освобождаются до завершения controller, ссылки на plugin interfaces явно освобождаются при ещё живых host context/handler. `terminate()` компонента вызывается только после успешной инициализации. Регрессия проверяет отказ initialize и обращение к host из деструктора processor.

Файлы: `plugins/Vst3/Vst3Instance.cpp/.hpp`.

### P1 — VST2 мог выйти за границы массивов каналов после IOChanged

Плагин может изменить число входов/выходов при автоматизации или MIDI program change. Перезапуск доставляется асинхронно, но старый код сразу использовал новые значения `AEffect::numInputs/numOutputs` с буферами прежнего размера.

Перед каждым сегментом и после доставки MIDI проверяется соответствие каналов выделенным массивам. При расхождении запрашивается restart, возвращается Error и обнуляется весь выходной блок, включая уже обработанную часть. Это исключает обращение хоста к старым массивам с новыми индексами. Тест меняет 2 канала на 6 в середине блока, затем проверяет восстановление после деактивации/активации.

Файлы: `plugins/Vst/VstInstance.cpp/.hpp`.

### P1 — Невалидные потоки состояния VST3/CLAP

Запись state не имела практического ограничения размера; VST3 seek допускал переполнение знакового сложения. Нулевая запись после большого seek могла выделять огромный разреженный буфер. Усечённая controller-часть VST3-state могла быть молча пропущена.

Добавлены проверки указателей и арифметики, ограничение 256 MiB на поток состояния, корректная обработка ошибки выделения памяти и запоминание ошибки записи, даже если плагин её проигнорировал. VST3-контейнер проверяется полностью до применения state: размеры обеих частей и точный остаток. Нулевая запись не выделяет память. Для VST3 лимит применяется отдельно к component и controller; максимальный контейнер — 512 MiB + 12 байт. Для CLAP — 256 MiB целиком. Этот новый лимит не распространён на VST2/AU.

Компромисс совместимости: необычно крупный state теперь отклоняется. Размер загруженной библиотеки сэмплов не равен размеру state, однако инструменты, встраивающие аудио непосредственно в state, могут попасть под лимит.

Файлы: `plugins/Vst3/Vst3Support.hpp`, `plugins/Vst3/Vst3Instance.cpp`, `plugins/Clap/ClapInstance.cpp`, `plugins/Host/PluginTypes.hpp`.

### P2 — CLAP терял запросы хоста во время init

Старый порядок вызывал `plugin->init()` с пустым `host_data`. При этом CLAP разрешает полноценные host callbacks во время init; запрет относится к factory `create_plugin`. Законные request_callback/request_process могли теряться.

Теперь сначала создаётся wrapper и устанавливается host_data, затем вызывается init, после него запрашиваются расширения. При отказе init экземпляр уничтожается однократно. Регрессия проверяет доставку request_callback, запрошенного из init. Контракт сверялся с vendored `third_party/clap/include/clap/plugin.h`.

Файлы: `plugins/Clap/ClapFactory.cpp`, `plugins/Clap/ClapInstance.cpp/.hpp`.

### P2 — Квадратичный поиск очередей параметров VST3

Для блока с N изменениями разных параметров поиск очередей выполнял O(N²) сравнений; `addParameterData` дополнительно искал индекс найденной очереди. Это особенно заметно при массовой синхронизации пресетов и плотной автоматизации.

Используется заранее выделенная таблица с открытой адресацией. Сохраняются порядок перечисления очередей, повторное использование одной очереди для одинакового ParamID и отказ без выделения памяти при исчерпании ёмкости. В аудиопотоке не появились блокировки или выделения памяти. Для пустой очереди очистка возвращается сразу, без сканирования таблицы.

Файл: `plugins/Vst3/Vst3Support.hpp`. Проверяются повторные и разреженные ID, коллизии, UINT32_MAX, переполнение пула, очистка и расширение вне обработки.

## Проверка настоящего RCompressor

Установленный модуль: `C:\Program Files\Common Files\VST3\WaveShell1-VST3 14.12_x64.vst3`, версия файла **14.12.90.381**. Класс RCompressor Stereo: `5653545552435372636F6D7072657373`. Основной вход/выход — stereo, дополнительный вход — stereo, latency — 64 сэмпла.

Тест: синус 220 Hz, амплитуда 0.5, 48 kHz, 256 блоков по 512 сэмплов; Threshold −42 dB, Ratio 50:1, Attack 0.50 ms. На последнем блоке RMS:

| Условие | Вход | Выход L | Выход R |
| --- | ---: | ---: | ---: |
| Эмуляция прежнего дефекта: активный пустой sidechain | 0.347322 | 0.362691 | 0.362691 |
| Исправленный realtime, sidechain не подключён | 0.347322 | 0.005801 | 0.005801 |
| Исправленный offline, sidechain не подключён | 0.347322 | 0.005801 | 0.005801 |

Различие RMS входа/выхода в контрольном варианте объясняется в том числе задержкой и фазой границы блока; это не измерение усиления с выравниванием задержки. Для вывода важна выраженная компрессия после отключения неиспользуемого key bus. Эмуляция старого дефекта использует тот же исправленный бинарник с принудительно активной пустой шиной, не отдельную старую сборку. Проверена stereo-версия, а не все варианты и версии Waves.

В sandbox первый диагностический запуск ожидал недоступный пользователю диалог выбора Waves folder. Его остановили; дальнейшие проверки запускались с доступом к установленной конфигурации Waves. Отсутствие этого окна у пользователя не было причиной дефекта DSP.

Воспроизведение из каталога проекта:

```powershell
build-windows/bin/plugin_probe.exe vst3 'C:\Program Files\Common Files\VST3\WaveShell1-VST3 14.12_x64.vst3' 5653545552435372636F6D7072657373 --set 1 0.3 --set 3 0 --set 2 0 --blocks 256
# Добавить --offline для offline-обработки.
# Добавить --sidechain-silent для эмуляции прежнего дефекта.
```

Значения `--set` здесь соответствуют представлению параметров именно этого Waves: вывод диагностики дополнительно показывает реальную подпись −42 dB / 50:1 / 0.50 ms. Их нельзя универсально переносить на другой плагин.

## Производительность

`plugin_parameter_bench` — отдельный opt-in микробенчмарк, не timing-gated CTest. Он создаёт очереди заранее, затем для каждого из 256 блоков очищает и заполняет их различными параметрами с одной точкой; результат — медиана трёх повторов. Измерена работа очередей хоста, не DSP компрессора и не время экспорта проекта.

| Изменённых параметров в блоке | До, ms | После, ms | Ускорение участка |
| --- | ---: | ---: | ---: |
| 128 | 1.4395 | 0.3150 | 4.6× |
| 1024 | 76.6774 | 2.5649 | 29.9× |
| 4096 | 1301.7700 | 11.5802 | 112.4× |

Это последовательные измерения на одной машине; фоновая нагрузка влияет на абсолютные значения. Повтор после завершения сборок дал 0.1838 / 1.4968 / 6.7727 ms соответственно; для таблицы сохранён первый замер после изменения, без подстановки самого быстрого результата. Ускорение целого тяжёлого проекта будет зависеть от доли автоматизации, DSP и диска. Отдельные ранее выполненные изменения и измерения полного рендера описаны в `render-review.md` рядом с этим отчётом.

```powershell
cmake --build build-windows --target plugin_parameter_bench -j 6
build-windows/bin/plugin_parameter_bench.exe
```

## Тесты и оставшиеся ограничения

Собраны затронутые библиотеки и диагностические/test targets в существующей Windows Release-конфигурации, MSVC 14.44. Финальный прогон: **16/16 CTest-наборов прошли**, 12.99 s, включая завершение процессов после освобождения Windows VST3-кэша. `git diff --check` по изменённым исходникам плагинов/графа/тестов не выявил ошибок пробелов. Это не полный прогон всего репозитория или UI приложения.

Регрессионный набор включает `plugin_contract_test`, `plugin_vst_test`, `plugin_vst3_test`, `plugin_host_test`, `plugin_midi_test`, `plugin_scan_test`, `plugin_insert_test`, `plugin_render_state_test`, `plugin_batch_test`, `engine_graph_test`, `render_test`, `render_safety_test`, `render_integrity_test`, `processing_render_test`, `track_freeze_test`, `recovery_test`.

```powershell
ctest --test-dir build-windows --output-on-failure -R '^(plugin_contract|plugin_vst|plugin_vst3|plugin_host|plugin_midi|plugin_scan|plugin_insert|plugin_render_state|plugin_batch|engine_graph|render|render_safety|render_integrity|processing_render|track_freeze|recovery)_test$' -j 4
```

Проверка безопасности здесь ограничена ошибками взаимодействия хоста с нативными плагинами. Плагины DSP продолжают выполняться внутри процесса: произвольный DLL может испортить память, зависнуть или обращаться к файлам с правами приложения. Проверки массивов и размеров state не превращают нативный код в песочницу. Изоляция обработки в отдельном процессе не реализовывалась.

Полный исходный пользовательский `.vlt` с коммерческими плагинами в рамках этой проверки не прошёл подтверждённый end-to-end экспорт. Поэтому исправление конкретного механизма Waves и прохождение регрессий не равны доказательству, что все первоначальные симптомы позднего/одностороннего появления инструментала устранены. Перед выпуском нужен контроль этого проекта в приложении и отдельный прогон AU на macOS. Установщик по просьбе пользователя не собран.
