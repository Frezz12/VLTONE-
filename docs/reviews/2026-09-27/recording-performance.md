Главный вывод: **Auto Strip Silence может заметно ухудшить отзывчивость после записи и увеличить DSP-нагрузку в следующих проходах. **Находки по убыванию практической важности**

**1. [P1] Неактивные Clip FX продолжают потреблять DSP; Strip Silence размножает их. Подтверждено кодом и измерением.**

[`sliceSilenceRegion()`](D:/Code/DAW/controller/StripSilence.cpp:132) копирует модель клипа и присваивает каждому insert новый ID. [Построение графа](D:/Code/DAW/controller/EngineController.cpp:3557) создаёт для каждого такого клипа отдельную цепочку player → inserts → fader → meter. На время новой записи [`syncTrackClips()`](D:/Code/DAW/controller/EngineController.cpp:2806) очищает списки воспроизведения, но сами цепочки остаются в графе.

[`PluginNode`](D:/Code/DAW/plugins/Host/PluginNode.cpp:635) пропускает обработку только после явного разрешения плагина на сон. Встроенный [EQ](D:/Code/DAW/plugins/Internal/EqualizerInstance.cpp:1174), [VST3](D:/Code/DAW/plugins/Vst3/Vst3Instance.cpp:1200) и [VST2](D:/Code/DAW/plugins/Vst/VstInstance.cpp:624) возвращают Continue. Поэтому разнесённые во времени фрагменты могут обрабатывать тишину всеми экземплярами на каждом блоке.

Первый практический шаг — исключать ненужные старые Clip FX из исполняемого графа записываемой дорожки в соответствии с уже принятой семантикой «старый материал не звучит во время дубля». Следующий — управление активностью цепочки по интервалам клипа при воспроизведении, с корректным прогревом, хвостами и событиями плагина. Нельзя просто усыплять любой плагин по нулевой амплитуде или разделять один изменяемый экземпляр между независимыми клипами.

Условие важно: **обычный новый клип без Clip FX не размножает эффекты дорожки.** Риск особенно относится к ручному Strip Silence существующего клипа с эффектами и к auto-обработке punch/layers, наследующих Clip FX.

**2. [P1] Завершение записи выполняет длинную последовательность работ в GUI-потоке. Подтверждено кодом и измерением.**

[`MainWindow::stopRecordingNow()`](D:/Code/DAW/app/MainWindow.cpp:15753) синхронно вызывает контроллер. Дальше [остановка recorder](D:/Code/DAW/core/Recording/RecordingEngine.cpp:328) ждёт завершения producer и делает join writer, который дописывает файл и заголовок. Размещение записи затем может вызвать [`loadSamples()`](D:/Code/DAW/controller/EngineController.cpp:1525): полное декодирование WAV, создание PCM и построение waveform. При Auto добавляется [анализ всего материала](D:/Code/DAW/controller/EngineControllerSilence.cpp:214), создание фрагментов и публикация графов.

Поэтому Stop может блокировать обработку ввода и перерисовку уже без Auto; Auto добавляет работу поверх этого. Замер восьми минутных дорожек — около 0,38 с без Auto и 0,50 с с Auto. Декодирование в [SampleLoader](D:/Code/DAW/controller/SampleLoader.cpp:20), построение [WaveformCache](D:/Code/DAW/controller/WaveformCache.cpp:76) и анализ Strip Silence проходят по аудио отдельными проходами.

Рациональная оптимизация: быстро зафиксировать окончание capture на границе аудиоблока; закрытие writer, подготовку PCM/peaks и анализ выполнять как отменяемую фоновую работу на неизменяемых данных; готовый результат применять одной транзакцией GUI. Уже есть асинхронный анализ в [ручном диалоге](D:/Code/DAW/app/StripSilenceDialog.cpp:243), поэтому общий путь подготовки можно переиспользовать. Успешное сохранение нельзя объявлять до проверки результата writer.

Live-envelope recorder имеет шаг около 25 мс, а strip-envelope — около 1 мс. Подмена одного другим изменит результат определения границ. Для повторного использования нужен подходящий более точный envelope, вычисляемый вне callback, и учёт comp/stretch/fades.

**3. [P1] Auto может временно заглушить весь выход при punch-out из-за сохранения/восстановления Clip FX. Подтверждено кодом; длительность зависит от плагинов.**

Auto-ветка [снимает состояния плагинов](D:/Code/DAW/controller/EngineController.cpp:18171) со всех старых клипов записанной дорожки ещё до проверки фактических разрезов. `applyStripSilence()` повторно снимает состояния затрагиваемых клипов. [`captureLibraryPlugins()`](D:/Code/DAW/controller/EngineController.cpp:19674) выполняет saveState под RenderGate; [`restoreLibraryPluginStates()`](D:/Code/DAW/controller/EngineController.cpp:19860) держит один общий gate на весь обход и loadState.

[Закрытый RenderGate](D:/Code/DAW/engine/Engine/RealtimeEngine.cpp:216) возвращает нулевой выход и не продвигает транспорт. При этом [finalizeRecordingCapture](D:/Code/DAW/controller/EngineController.cpp:18017) специально оставляет воспроизведение включённым для punch-out. Значит, сопровождение или мониторинг могут прерываться независимо от среднего CPU. При 64 сэмплах даже несколько миллисекунд save/load перекрывают несколько блоков.

Следует убрать повторные снимки и восстановление неизменённых экземпляров; новые экземпляры загружать до публикации в работающий граф, использовать проверенный кэш состояний. **Убирать RenderGate без изменения жизненного цикла нельзя:** многие плагины не допускают save/load одновременно с process. Во время самой текущей записи auto-анализ не запускается; описанный путь относится к завершению/punch-out.

**4. [P2] Auto перестраивает весь граф отдельно для каждой записанной дорожки. Подтверждено счётчиком.**

[`finalizeRecordingCapture()`](D:/Code/DAW/controller/EngineController.cpp:18135) перестраивает граф; каждое изменившее клипы [`applyStripSilence()`](D:/Code/DAW/controller/EngineControllerSilence.cpp:177) делает ещё одну пересборку и восстановление состояний; [конец `stopRecording()`](D:/Code/DAW/controller/EngineController.cpp:18226) снова перестраивает граф. При N изменившихся дорожках получается N + 2 публикаций вместо двух в обычном пути: 10 на восьми дорожках.

Следует сначала рассчитать все изменения, затем применить их одной операцией с одной итоговой пересборкой. Снятие recorder taps и переход мониторинга должны сохранить правильную границу; необязательно объединять все стадии в единственную небезопасную публикацию. Измеримый критерий — количество полных rebuild не должно линейно расти с числом записанных дорожек.

**5. [P2] Короткий punch анализирует всю длину старого layered-клипа. Подтверждено кодом и измерением.**

В [`stripRecordedSilence()`](D:/Code/DAW/controller/EngineControllerSilence.cpp:215) envelope строится на `source.durationSeconds`. Только после этого вычисляются пересечения с записанными passes и возвращаются нетронутые области. Поэтому 0,5 секунды записи в середине 10-минутного клипа потребовали около 131 мс вместо 0,8 мс без Auto.

Анализировать нужно объединение записанных интервалов с достаточным контекстом для hysteresis, minimum silence/sound, pre/post-roll и grid. Остальные диапазоны сохранять без повторного полного анализа. Проверки должны сравнивать результат с нынешним алгоритмом, включая comp, stretch и граничные звуки.

**6. [P2] Count-in зависит от GUI-таймера и готовит recorder уже на финальной доле. Подтверждено кодом.**

[Таймер имеет интервал 8 мс](D:/Code/DAW/app/MainWindow.cpp:1203). По его сигналу [`tickCountIn()`](D:/Code/DAW/controller/EngineController.cpp:17437) вызывает запуск, который [выделяет ring buffers, создаёт WAV и writer threads](D:/Code/DAW/controller/EngineController.cpp:17318), перестраивает граф и лишь затем публикует recorder. Это добавляет задержку после срабатывания таймера, особенно на нескольких дорожках.

Точное размещение по фактическому входному блоку уже есть, но оно не делает начало захвата относительно последнего клика sample-accurate. Подготовку файлов и буферов следует завершать во время count-in, а начало capture назначать на заранее вычисленную позицию аудиочасов. Это вопрос момента старта, отдельный от непрерывной нагрузки уже запущенной записи.

**7. [P2] История записи занижает свой расход памяти и копирует большие снимки. Подтверждено кодом.**

[`stopRecording()`](D:/Code/DAW/controller/EngineController.cpp:18221) захватывает `landings` по значению в двух closures, каждый содержит before/after для всех затронутых дорожек. В `UndoStack::push()` не передаётся размер. [Значение по умолчанию — 256 байт](D:/Code/DAW/controller/UndoStack.hpp:44), хотя фактическая память моделей может быть на порядки больше. Поэтому лимит истории в 128 MiB не отражает её реальный размер для записи. Ограничение в 100 действий всё ещё действует.

После Strip Silence объём дополнительно растёт: каждый фрагмент копирует список takes и plugin metadata. Нужен один общий неизменяемый снимок для undo/redo и корректный estimatedBytes, по аналогии с ручным Strip Silence. Сначала исправить учёт; удалять takes, ещё нужные для компинга/отмены, нельзя. Это вероятный источник деградации после многих дублей, а не доказанный источник каждого короткого xrun.

**8. [P2] Индикатор Audio CPU не объясняет все виды сбоев. Подтверждено кодом.**

[`dspLoad`](D:/Code/DAW/engine/Engine/RealtimeEngine.cpp:277) — сглаженное время renderBlock. [Запись входа](D:/Code/DAW/controller/EngineController.cpp:1173) происходит позже и в этот показатель не входит. Gated-блок возвращается до обновления dspLoad. GUI-работа после Stop также в нём отсутствует.

Полные времена callback уже собирает [AudioDeviceManager](D:/Code/DAW/core/Device/AudioDeviceManager.cpp:764); есть отдельные счётчики xruns, gated blocks и потерь записи. Стоит вывести диагностическое представление: p99/p99.9/max callback, превышения бюджета, device xruns, gated blocks, PCM misses и recording dropped frames. Статистику считать вне callback. Усреднённый процент оставить как общий индикатор, но не использовать его для вывода «лагов быть не должно».

**Дополнительные места, где оптимизацию нужно подтверждать профилем**

- **Планировщик на малых буферах.** [Выбор parallel path](D:/Code/DAW/engine/Graph/GraphProcessor.cpp:234) зависит от числа узлов и ширины графа, без оценки стоимости DSP конкретного блока. Это не подтверждает scheduler как основную причину описанных лагов; более тяжёлые плагины, 32 frames и драйвер требуют отдельного профиля. [Лог](D:/Code/DAW/artifacts/recording-performance-review/scheduler-bench-valid.log).
- **Первое выделение PCM-кэша.** [SampleStorage](D:/Code/DAW/engine/Memory/SampleStorage.cpp:48) использует mapping начиная с 1 MiB или при исчерпании heap budget. Первый такой [SampleBuffer](D:/Code/DAW/engine/Audio/SampleBuffer.hpp:26) создаёт [фиксированный PCM pool](D:/Code/DAW/engine/Memory/PcmReadCache.cpp:21) на 256 MiB, обнуляет его, пробует VirtualLock и запускает worker. Если первое большое аудио появляется после записи, эта подготовка попадает на путь Stop. Переносить её в подготовку аудиосессии или фоновую подготовку ресурса; отдельно измерить холодный старт.
- **PCM misses.** [Cache miss возвращает тишину](D:/Code/DAW/engine/Memory/PcmReadCache.cpp:189), а [фоновый reader](D:/Code/DAW/engine/Memory/PcmReadCache.cpp:147) обслуживает запросы с prefetch и паузой 1 мс при простое. При seek/многих источниках/давлении памяти возможен дефицит готовых страниц. Предвыборка уже есть, поэтому сам интервал 1 мс не доказывает проблему. Проверять misses, очередь запросов и фактический locked memory.
- **Обновление warped clips.** [ClipPlayerNode::setClips](D:/Code/DAW/engine/Nodes/PlaybackNodes.hpp:91) для каждого warped placement ищет прежний экземпляр линейным обходом. Это O(N²) при большом числе таких placements во время синхронизации/пересборки. Индекс прежних экземпляров по идентичности clip/audio уберёт повторные поиски; это работа control thread, не текущего render.
- **Много одновременных WAV writers.** У каждого recorder отдельный поток с [опросом раз в 5 мс](D:/Code/DAW/core/Recording/RecordingEngine.cpp:501). При десятках дорожек стоит измерить wakeups и конкуренцию за диск/CPU. Этот интервал не означает задержку мониторинга на 5 мс: callback пишет в ring с запасом около четырёх секунд. Не переносить запись файла в callback ради сокращения числа потоков.
- **Постоянная задержка мониторинга.** [PDC учитывает latency плагинов](D:/Code/DAW/engine/Graph/AudioGraph.cpp:286) в маршруте, включая входное мониторирование. Малый hardware buffer не убирает lookahead/FFT/linear-phase latency. Вычитание этой задержки при размещении записи корректирует положение клипа, но не ускоряет слышимый монитор. Для диагностики показывать отдельно device latency и graph/plugin latency; режим низкой задержки должен явно определять политику для таких плагинов, а не просто отключать компенсацию.

**Что уже сделано правильно и не следует ломать**

Запись передаёт данные из callback через ограниченный ring, дисковый writer вынесен в отдельный поток. Есть счётчики потерь и сохранение временных дыр вместо сдвига последующего материала. Realtime snapshot reclamation, интервальный индекс обычных клипов, task fusion, MMCSS, prefetch и защита от denormals уже присутствуют. Фоновое снятие recovery plugin state откладывается при live audio activity — периодический autosave не следует объявлять причиной только по наличию saveState в проекте. Master spectrum уже ограничивается наличием потребителей.

Критерий для новых изменений: не добавлять в callback I/O, выделение памяти или блокирующие locks. Эти ограничения соответствуют [официальным рекомендациям PortAudio](https://files.portaudio.com/docs/v19-doxydocs/writing_a_callback.html). Перенос тяжёлой операции в worker сам по себе не делает безопасным одновременное изменение живого plugin instance.
