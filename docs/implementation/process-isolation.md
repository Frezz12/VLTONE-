# Изоляция исполнения: плагины, аудиопроцесс и рабочие задания

Текущий статус на 8 октября 2026 года. Обычный `EngineController` использует `AudioRuntimeEndpoint`: граф, устройство, транспорт, запись и встроенный DSP исполняются в `daw_audio`. Внешний экземпляр плагина получает свой `daw_plugin_host`; экспорт и файловые задания выполняются в `daw_worker`. Документ, Undo и интерфейс остаются в приложении. Автоматического возврата к движку в UI при отсутствии помощника нет. Нативное исполнение той же реализации доступно только явно выбранным владельцам `TestRuntime` и `WorkerRuntime`.

`MainWindow` выбирает `HostingMode::Isolated` до инициализации контроллера. Переключатель `plugins/isolatedHosting` удалён; отсутствие helper возвращает ошибку. Копирование каталога переносит конфигурацию в черновики и задания. Низкоуровневый локальный адаптер остаётся внутри самого plugin host и тестов форматов. Это одна реализация DSP с разными владельцами исполнения, а не два аудиодвижка.

| Часть | Фактическое состояние |
| --- | --- |
| Внешние CLAP, VST3, VST1/2, AU | Общий процессный адаптер, сбой и перезапуск отдельного экземпляра; Windows fixtures проверены, AU требует macOS |
| Экспорт, нормализация, анализ микса/канала | `daw_worker`; исходный граф не изменяется, файлы публикуются после успешного завершения задания |
| Граф, транспорт, устройство, запись, встроенные модули | Владелец `AudioRuntime`; самостоятельный backend `AudioRuntimeProcess` исполняет их в `daw_audio` |
| Основной интерфейс → аудиопроцесс | Процессный endpoint по умолчанию; broker, пакетные показания и восстановление поколения |
| Ресурсы и команды | Версионируемый bounded codec, неизменяемый PCM, сессии/поколения/ревизии, процессные транзакции и типизированные команды |
| Прослушивание черновиков | Общий механизм runtime; старый `EngineController::PluginAuditionNode` и его callback в контроллер удалены |
| Декодирование файлов, probe, темп/тональность, pitch, transients, Slicer | `MediaWorker` поверх общего `WorkerJob`; производственные точки входа перенаправлены в `daw_worker` |

`AudioRuntimeProcess` держит первичную сессию устройства и числовые вторичные сессии. Черновик переключается внутри ребёнка, без передачи аудиоблоков через UI. Неудачное обновление графа восстанавливает опубликованные узлы, управляющие значения, расписания и ожидающие MIDI-события. Создание/активация новых плагинов подготавливается до блокировки публикации. Транзакция сохраняет также ревизию, PCM и журнал родителя; после отката перезапуск не должен вернуть отменённую проекцию. Перезапуск не возобновляет воспроизведение, запись или прослушивание автоматически.

`AudioRuntimeRpc` связывает команды с существующими методами runtime. Выходные ссылки и spans превращаются в полностью проверенные owned values. Большие сообщения используют приватные файлы, PCM — реестр отображаемых ресурсов. Ограничены байты сообщения, число элементов и суммарная память декодирования. Управляющие вызовы синхронны; `AudioRuntimeEndpoint` обслуживает частые UI-геттеры через пакетное обновление показаний и кэш. Журнал ведётся выше уровня RPC: native state попадает в checkpoint, структура — в `applySession`, подтверждённые host controls и изменения источников — в `AudioRuntimeDurableEdits`.

Удалены прямой экспорт живого графа и повторный DSP-проход нормализации. Нормализация читает результат одного прохода worker; отмена, ошибка и исключение до публикации сохраняют прежние выходные файлы. `RealtimeEngine`, DSP, PDC и адаптеры SDK переиспользуются внутри исполнителей.

Загрузка новой сессии и её обновление используют один `AudioRuntime::applySession`: новые экземпляры, импорт состояния проекта и native checkpoints подготавливаются до публикации. Импорт не может незаметно изменить уже звучащий здоровый экземпляр. При неудаче сохраняются прежний граф и его состояния; формат устройства и поколения проверяются отдельно. Обновление в том же поколении допускается во время записи, поскольку идентификаторы рекордеров и их входы принадлежат отдельному реестру. Замена поколения и смена формата во время записи запрещены.

Политика отсутствующих плагинов задаётся для каждого слота: `Required` для явной вставки, `PreserveUnavailable` для импортируемого документа и `PlaceholderOnly` для заблокированного состояния. Пустой `PluginNode` сохраняет место в цепи и пропускает аудио/MIDI, не притворяясь доступным плагином. Независимые состояния Dual Mono и исходные PCM удерживаются для последующей загрузки. Маркер `projectState` отличает исходный проектный chunk от native checkpoint: например, Sampler нельзя повторно загрузить как обычный native chunk после разрешения относительных путей Content.

Процессный checkpoint восстановления изолированного плагина использует подтверждённые результаты его DSP, включая последнюю рабочую копию уже упавшего экземпляра. Явный экспорт использует режим `Exact` и сохраняет ожидающие host edits. Эти режимы разделены: команда, ещё не прошедшая обработку и способная вызвать падение, не должна автоматически повторяться при восстановлении процесса. После перезапуска сбрасывается также флаг записи в проекции дорожки, чтобы её клипы снова участвовали в воспроизведении.

Сохранение шаблонов переиспользует `prepareProjectSave` / `writePreparedProject`; отдельный native writer удалён. Состояния отсутствующих плагинов сохраняются в Save As, шаблонах и recovery даже после удаления исходного пакета. Кэш привязан к UID и формату, поэтому замена плагина в том же слоте не переносит opaque state предыдущего экземпляра.

Основной контроллер подключён к процессному клиенту. Отрисовка использует кэш снимков, начальное значение редактирования считывается явно, MIDI использует общий clock с поколением, файловые задания отправляются worker. Оставшиеся условия приёмки и ограничения управляющего UI перечислены в конце отчёта.

Ниже сохранена история шагов 7 октября; описания тогдашних ограничений следует читать вместе с текущим статусом выше.

Один экземпляр `PluginProcess` владеет одним процессом. Два экземпляра одного DLL имеют разные PID, память и состояние. Отсутствующий helper вызывает явную ошибку; автоматического перехода к загрузке этого экземпляра в родительском процессе нет.

На Windows процесс создаётся сразу внутри Job Object с завершением детей при закрытии последнего дескриптора задания. Передаётся явный список дескрипторов; стандартные потоки перенаправлены в NUL. Это исключает промежуток между созданием ребёнка и назначением задания, описанный в [документации Microsoft](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812). POSIX-реализация использует `posix_spawn`, приватную отображаемую память, группу процессов и отдельный поток наблюдения за каналом жизни родителя; на этой машине она не собиралась и не проверялась.

Изоляция ограничивает последствия аварии процесса. Ограничение файловых/сетевых прав плагина в этот этап не входит.

## Обработка блока

1. `submit()` проверяет размеры и события, копирует входы в подготовленную память, публикует номер запроса и будит ребёнка. Одновременно разрешён один незавершённый блок.
2. Ребёнок копирует данные в свои заранее выделенные буферы. Плагин не получает указателей на протокол и общую память. `startProcessing`, `stopProcessing`, reset и DSP исполняются одним выделенным аудиопотоком; управляющие вызовы — основным потоком ребёнка.
3. `poll()` немедленно возвращает `Pending`, пока ответа нет. Перед выдачей результата проверяются размеры, номера запросов, конечность всех аудиосэмплов и корректность всех событий. Только полностью проверенный результат публикуется вызывающему коду.
4. `GraphProcessor` опрашивает ожидающие задания небольшими порциями и освобождает зависимости только после завершения узла. В realtime все удалённые узлы используют один срок: 80% периода блока с момента начала прохода. Для offline действует общий защитный таймаут 10 секунд. По истечении срока незавершённого задания вызывается `expire()`; поздний ответ этого поколения больше не принимается. Выход неисправного экземпляра заполняется тишиной, удержанные выходные ноты снимаются. Доверенный MIDI passthrough аудиоэффекта сохраняет `note-off`. Независимые ветки сохраняют свой сигнал; явный bypass остаётся доступен. Если следующий удалённый узел ещё не начал работу к истечению срока, его блок пропускается с безопасным выходом, а процесс и очередь host edits сохраняются: зависший предшественник не должен отключать исправного потомка.
5. После остановки обращений рендера управляющий поток вызывает `service()` для обнаружения/завершения неисправного процесса либо `restart()` для создания нового.

`submit`/`poll` не выделяют память, не спят и не ожидают завершения DSP. `PluginNode` делит обработку на `beginProcess`/`finishProcess`; подготовка входов и окончательная обработка результата общие для локального и удалённого экземпляра. Планировщик продолжает готовые независимые задания, пока ребёнок обрабатывает звук. Даже при одном потоке графа несколько независимых процессов могут исполняться одновременно. Обычные графы сохраняют прежний быстрый последовательный путь. Удалены неиспользуемые `JobSystem::dispatch`/`notifyCompleted` и дублирование планирования прохода.

Обмен завершается в том же блоке: дополнительный блок задержки и новая PDC-поправка не вводятся. Это не означает нулевую стоимость IPC: последовательная цепь по-прежнему оплачивает каждый обмен и может исчерпать общий срок. Промах срока помечает экземпляр неисправным до явного перезапуска. Прямой вызов `PluginNode::process` имеет ограниченный совместимый путь ожидания; штатный граф использует двухфазный интерфейс.

Обычные управляющие операции имеют таймаут (по умолчанию 10 секунд). Они не должны пересекаться с незавершённым аудиоблоком. API рассчитан на одного сериализованного владельца; атомарный код ошибки не делает остальные методы безопасными для произвольных параллельных вызовов. В частности, `service`, `close`, `restart` и уничтожение объекта выполняются вне realtime после остановки обращений рендера.

Протокол версии 5 переносит аудио, sidechain, MIDI/нотные и параметрические события, pitch ramps и transport. Заголовок занимает 384 байта. Управляющий и аудиоканалы имеют отдельные номера запросов и сигналы пробуждения. Внеблочные значения и begin/end жестов проходят через кольцо из 2048 записей по 16 байт; повреждённое событие или переполнение отключает экземпляр с диагностикой, а не молча теряет жест. Лимиты фиксируются на время жизни процесса. Графовый адаптер начинает с 512 кадров, 32 каналов, 4096 аудиособытий и по 1 МиБ для текста и бинарной части команды. Перед активацией ёмкость рассчитывается по существующему бюджету `pluginBlockEventCapacity`: инструменты получают полный запас полифонических pitch-событий, эффекты — запас автоматизации и host edits. При росте создаётся новый процесс с сохранённым состоянием; это происходит только при остановленной обработке. Нельзя молча усечь события или расширить память в callback. Совместимость версии, размеров записей и общей памяти проверяется до загрузки нативного кода.

В дочернем процессе выделенный аудиопоток и диспетчер аудиоканала регистрируются через существующий `AudioWorkerRegistration`; конфигурация приоритета подтверждается до завершения активации. Ожидающий диспетчер спит на сигнале без периодического опроса. Reset для форматов, допускающих его в realtime, передаётся с ближайшим блоком; legacy-reset с переходами активации выполняется управляющим потоком. Контроллер VST3 получает итоговые значения автоматизации после DSP, чтобы событие на кадре 37 не начинало действовать с кадра 0. Значения в родительском адаптере атомарны. Запрос `pumpMainThread` из live UI использует отдельный атомарный флаг и пробуждение, не занимая mailbox активного аудиоблока.

## Состояние и восстановление

Состояние передаётся порциями через ограниченный буфер; общий размер ограничен существующим `kMaxPluginStateBytes`. На всю передачу действует один управляющий таймаут. Новый снимок становится подтверждённым только после успешной операции целиком. Ошибка или краш при сохранении сохраняют предыдущие байты и в объекте хоста, и у вызывающего кода.

Низкоуровневый `restart()` завершает старый процесс и восстанавливает его из снимка при остановленном доступе рендера. Пользовательская команда `EngineController::restartInsert` работает иначе: фоновая задача создаёт и полностью подготавливает новый `PluginNode`, а управляющий поток публикует его после проверки результата. Загрузка и активация не держат live RenderGate. ID слота, маршрутизация, автоматизация, mix и bypass сохраняются. Для dual mono готовятся только отказавшие стороны; готовность обеих сторон проверяется до замены.

Подтверждённый непрозрачный снимок дополняется журналом параметров: только завершённые DSP-блоки и полученные callbacks редактора обновляют подтверждённые значения. Восстановление сопоставляет параметры по стабильным ID. Изменение из аварийного блока не воспроизводится повторно. Проект и Undo могут сохранять последний снимок упавшего плагина вместе с подтверждёнными значениями. Экспорт с отказавшим live-экземпляром явно отклоняется: старый снимок не выдаётся за актуальный результат. Приватные изменения состояния после последнего успешного сохранения, текущие голоса и хвост эффекта восстановить нельзя.

В локальном JSON параметр, подтверждённый после аварийного снимка, получает необязательный признак `restoreAfterState`. При успешном чтении opaque state повторно применяются только помеченные значения; обычная резервная таблица не перекрывает preset. Сохранение исправного экземпляра обновляет снимок и снимает признак. Undo удаления хранит сами байты состояния и подтверждённые/ожидающие параметры обеих сторон, а не только путь к прежнему файлу. Публикация проекта с отказавшим live-плагином отклоняется до его восстановления.

Готовая фоновая задача проверяет исходные экземпляры обеих сторон, ID слота, аудиоконфигурацию, ширину и sidechain. Удаление, Undo, замена слота и новый проект не позволяют позднему результату заменить другое поколение. Повторная команда во время восстановления не запускает второй процесс. Неудачная попытка оставляет слот доступным для повторного ручного перезапуска.

Добавлено точное значение `ClapInstance::isProcessing()`: статус теперь отражает `start_processing`, а не только факт активации. Это позволяет хосту обнаружить отказ плагина начать обработку.

## Окна и события редактора

При сборке приложения `daw_plugin_host` использует Qt Widgets. Нативный родитель и редактор плагина создаются в одном дочернем процессе; HWND/NSView не пересылаются в DAW. Это сохраняет платформенный контракт [встраивания нативного окна Qt](https://doc.qt.io/qt-6/mixing-qt-with-other-ui-toolkits.html). Управляющий поток обслуживает события Qt и legacy editor idle примерно раз в 16 мс; аудиодиспетчер использует независимое пробуждение. Зависание открытия GUI поэтому не удерживает аудиоканал. Запросы открытия/закрытия асинхронны и имеют watchdog; падение процесса обнаруживается отдельно.

Для исправного внешнего плагина с собственным GUI DAW открывает только одно окно в `daw_plugin_host`. Повторный вызов поднимает это же окно и восстанавливает его из свёрнутого состояния; окно DAW с кнопкой открытия рядом не создаётся. На Windows перед показом передаётся разрешение на активацию конкретному процессу плагина. Межпроцессное родительство HWND не используется: оно связывает очереди ввода и может задерживать UI хоста при зависании редактора.

Панель DAW остаётся для параметров плагина без GUI и для восстановления после отказа. Пункт «Параметры и маршрутизация…» в меню вставки, инструмента и вложенных эффектов переключает собственный GUI плагина на ту же панель: сохраняются выбор стороны Dual Mono, сайдчейн, Slide и доступ к параметрам для автоматизации. Кнопка открытия возвращает GUI плагина и закрывает панель. Контролы не дублируются, список параметров создаётся по явному запросу пользователя.

Отказ и восстановление также обозначаются текстом у слотов и инструментов микшера. Begin/value/end редактора передаются в прежний `PluginListener`; очередь ещё не обработанных редактором значений доступна сохранению и render clone. При сборке без приложения Qt не требуется, а helper не объявляет наличие нативного редактора.

Снимок редактора различает ожидающее открытие, открытое окно, отказ и закрытие. Фоновые окна на Windows обслуживаются через общий кэш показаний; синхронный опрос shortcuts остаётся только у активного редактора и при отключении его прежнего владельца фокуса. При смене стороны Dual Mono старое окно закрывается до регистрации нового. Отсоединение панели очищает все её токены: повторный вызов из отложенного деструктора не может отменить открытие преемника.

## Что проверено

Проверено на Windows x64, MSVC 2022, Release. Новый `plugin_process_test` использует отдельный исполняемый файл хоста и реальные CLAP-библиотеки. Проверки охватывают:

- независимые экземпляры одного DLL, отсутствие helper, несовместимую версию и ответ с некорректным размером;
- падение при создании, в DSP, при сохранении и восстановлении состояния;
- зависание активации, DSP и деструктора; ограниченное ожидание и завершение ребёнка;
- аварийную смерть родителя без вызова его деструкторов и завершение оставшегося хоста;
- поздний ответ после истечения дедлайна, NaN, ошибку обработки, превышение размера блока и неверное время события;
- запрет двух одновременных блоков и управляющей команды поверх незавершённого DSP;
- сохранение 32 КиБ состояния через буфер 4 КиБ и восстановление прежнего снимка после отказа;

## История этапа 4: владелец исполнения и независимый снимок сессии

Следующие подразделы сохраняют историю миграции и её проверок. Текущее состояние описано в начале документа и в разделе переключения приложения ниже.

Начат следующий этап разделения документа и исполнения. Это локальная граница владения; отдельного процесса основного движка пока нет.

- [`AudioRuntime`](../../controller/AudioRuntime.hpp) теперь единолично владеет `RealtimeEngine`, каналами и узлами, устройством, аудиоколбэком, опубликованным списком рекордеров, состоянием восстановления плагинов и точками захвата экспорта. Документ, Undo, облачные команды и редактирование остаются в `EngineController`. Старые поля и реализация `DeviceCallback` в контроллере удалены, ссылочных дублей владельца нет.
- Аудиоколбэк обращается только к runtime: тот же прямой вывод в буфер устройства, тот же порядок захвата сырого входа и учёта PDC. В аудиопуть не добавлены копии буферов, блокировки или межпроцессный обмен. Подготовка runtime общая для инициализации и смены конфигурации; ошибки подготовки/сборки графа больше не теряются в `initialize()`.
- [`RenderSessionSpec`](../../controller/RenderSessionSpec.hpp) удерживает неизменяемое поколение проекта, настройки рендера, каталог/режим хостинга, непрозрачные состояния и ожидающие параметры плагинов. `captureRenderSession()` работает на управляющем потоке; статический `renderSession()` создаёт независимый локальный runtime и не обращается к исходному контроллеру. Снимок можно исполнять после его уничтожения и повторно. Большие декодированные и обработанные аудиобуферы разделяются через неизменяемые ресурсы, без копирования PCM. Внешние файлы и библиотеки плагинов по-прежнему должны быть доступны.
- Обычный экспорт использует эти же функции. Рендер фиксирует свой снимок до progress callbacks; замена внешнего handle во время callback не меняет исполняемое поколение. Настройки проверяются до остановки транспорта. При независимом рендере дорожки захват состояния master-цепи больше не вызывается.
- Панели Compressor, CLA-2A, Delay, Graphit и Pitch получают общий [`EffectMeterSnapshot`](../../controller/PluginReadout.hpp), Sampler — `SamplerSnapshot` с удержанием аудиоресурса. Их рабочие пути не получают указателей на DSP; изменения параметров используют существующие команды контроллера и Undo. Доступность проверяется по слоту и UID. Это начало миграции встроенных редакторов, не завершение всех редакторов.
- Удалён служебный `AudioRecorder`, который создавался и настраивался только для записи готовых WAV. Существующий writer стал статическим; его реализация не дублируется. Копирование каталога плагинов использует тот же механизм снимка, что и detached render.

Новые регрессии проверяют рендер после закрытия исходного контроллера, повторное исполнение и отмену, замену handle из callback, очистку неудачного снимка, сохранение транспорта при ошибочном запросе, показания эффектов после обработки/удаления/Undo и удержание сэмпла после смены проекта.

Проверки этого шага выполнены в отдельной Windows x64 Release-сборке `build-audio-runtime`, чтобы не пересекаться с другими сборками в `build-windows`. Приложение собрано успешно. Перечисленные 23 теста прошли в целевых прогонах; повторный таймаут теста графа описан ниже:

| Документ, запись, редактирование | `controller_test`, `automation_test`, `recording_preview_test`, `midi_recording_test`, `audio_monitoring_regression_test`, `collaboration_protocol_test`, `track_freeze_test` |
| Рендер, плагины, восстановление | `render_integrity_test`, `render_isolation_integrity_test`, `plugin_render_state_test`, `plugin_recovery_test`, `plugin_isolation_graph_test`, `plugin_insert_test`, `recovery_test`, `plugin_contract_test`, `audio_realtime_test` |

Причина зависания не доказана; успешный повтор не закрывает этот дефект. Проверки реального устройства и коммерческих плагинов этим набором не заменяются.

### Продолжение этапа 4: встроенные редакторы и поколения экземпляров

Equalizer, Gravity, Modulation/Loom и Slicer переведены на типизированные команды и снимки [`EngineController`](../../controller/EngineControllerReadout.cpp). Рабочие пути этих панелей больше не получают `PluginInstance*`; прямой доступ в `checkForTest` оставлен только для подготовки и точного восстановления диагностической фикстуры. Служебные чтения Sampler в `AiChatPanel` используют существующий `SamplerSnapshot`.

- Типы Equalizer и Gravity выделены в `EqualizerParams.hpp`/`GravityParams.hpp`; `Slicer::ControlState` перенесён в общий `SlicerParams.hpp`. Панели и DSP используют одни определения. Сами алгоритмы фильтров и таблицы параметров не скопированы.
- Снимки содержат параметры полос, настройки анализатора, показания и метаданные пресетов. A/B использует существующие команды параметров и одну группу Undo. Повторный выбор активного A/B и неверный слот не размораживают дорожку; действительное переключение заново разрешает экземпляр после перестройки графа. Команды изменения звука и состояния учитывают права редактирования и lease совместной сессии.
- Кривые EQ и Loom запрашиваются отдельно при изменении параметров или частоты дискретизации. DSP по-прежнему рассчитывает их своими функциями. Повторные чтения состояния Slicer внутри циклов заменены локальным снимком; активность клавиш запрашивается только для обновления пэдов. PCM и таблицы слайсов передаются неизменяемыми shared handles, без копирования аудиоданных.
- `PluginIdentity` сочетает поколение проекта и монотонный ID `PluginNode`. ID выделяется при создании узла, включая восстановление в рабочем потоке, и не зависит от адреса объекта. Для dual mono выбирается ID соответствующей стороны. Транзакция Slicer и завершение фоновой задачи проверяют идентичность; удаление/Undo с тем же slot ID не позволяет применить результат старого экземпляра. Фоновая лямбда больше не хранит указатель DSP.

### Продолжение этапа 4: самостоятельная сборка графа в runtime

[`AudioRuntimeGraph.cpp`](../../controller/AudioRuntimeGraph.cpp) теперь собирает и публикует топологию: обычные и Dual Mono цепи, Mini Modules, инструменты, Sampler FX, Clip FX, входы, шины, посылы, sidechain, bounce injection, замороженное аудио и точки экспорта. Идентификаторы удалённых при заморозке узлов сбрасываются до подключения внешних маршрутов. Пропущенные при записи Clip FX используют тот же сброс; при остановке записи их экземпляры переиспользуются.

Вход сборщика — [`AudioGraphSpec`](../../controller/AudioGraphSpec.hpp): принадлежащие описанию значения маршрутизации и ссылки на неизменяемое декодированное аудио. Он не копирует весь проект, MIDI-ноты или состояния плагинов и не хранит указатель на контроллер либо обратные вызовы UI. Сборка новой топологии и её публикация разделены, поэтому создание треков и пакетное применение плагинов по-прежнему восстанавливают native state до включения новых процессоров в рабочий граф. Все управляющие пути публикации используют `AudioRuntime::commitGraph`.

[`EngineControllerGraph.cpp`](../../controller/EngineControllerGraph.cpp) готовит это описание: проверяет freeze и обратные связи sidechain, согласует экземпляры плагинов и уведомляет редакторы перед их удалением. После сборки runtime контроллер публикует клипы, MIDI и автоматизацию. Прежние функции соединения узлов и дублирующие обёртки удалены из контроллера; документ, Undo и команды остаются там.

Runtime выделен в отдельную CMake-библиотеку `daw_audio_runtime`, зависящую от движка, устройства и хоста форматов, без зависимости от `daw_controller`. [`audio_runtime_graph_test`](../../tests/audio_runtime_graph_test.cpp) линкуется только с этой библиотекой и её зависимостями. Аудиоколбэк, способ планирования и формат буферов не менялись; IPC и дополнительный блок буферизации в этот шаг не добавлены.

### Продолжение этапа 4: применение подготовленной сессии

[`AudioSessionSpec`](../../controller/AudioSessionSpec.hpp) объединяет описание топологии с подготовленными списками аудиоклипов, MIDI, контроллеров и автоматизации. Контроллер проецирует документ в эти данные, сохраняя у себя Undo, правила записи, геометрию клипов и идентификаторы голосов. [`AudioRuntimeContent.cpp`](../../controller/AudioRuntimeContent.cpp) применяет данные к собственным узлам; прямые вызовы публикации этих списков и кривых удалены из контроллера. Live MIDI также поступает через метод runtime.

Полная пересборка использует `buildSession`, а правки отдельных каналов — тот же `applyContent`. Отсутствующая секция оставляет соответствующее содержимое без изменений; присутствующая пустая очищает его, включая приватные проигрыватели Clip FX. Аудиоресурсы передаются через совместное владение, без копирования PCM в описание сессии. Посылы получают кривые по стабильным ID, в том числе при отсутствующем адресате другого посыла.

Runtime хранит нормализованные кривые плагинов и сам разрешает ID параметров в индексы и единицы конкретного экземпляра. После явной переконфигурации плагинов разрешение повторяется под `RenderGate`, до следующего аудиоблока, поскольку активация VST3 может заменить таблицу параметров. Повторно обходить документ и строить кривые для этого больше не требуется. Обе стороны Dual Mono теперь получают автоматизацию и очищают её после удаления lane; инструменты принимают как свой явный ID слота, так и прежнее пустое значение. ## Переключение приложения на процессное исполнение (8 октября)

`EngineController` больше не создаёт локальный runtime в обычном конструкторе. `AudioRuntimeEndpoint` обслуживает один broker; его поток владеет `AudioRuntimeProcess`. Редкие команды ждут подтверждения. Отрисовка читает пакетный кэш, а MIDI-время — generation-bound shared clock без синхронного IPC. Операции редактирования, которым нужен точный исходный снимок, явно выбирают `Readout::Current`: загрузка/очистка Sampler, Slicer, Undo параметров и A/B EQ не зависят от первого тика интерфейса.

Черновики используют числовые вторичные сессии того же аудиопроцесса. Публикация новой сессии сначала готовит плагины, PCM, параметры и непрозрачные состояния. При явном импорте состояния уже существующего плагина готовится новый экземпляр нужной стороны; плохой chunk оставляет прежние экземпляры. Обе стороны Dual Mono и их отдельные состояния удерживаются при восстановлении. Смена частоты/размера блока заменяет целое поколение, сохраняя подтверждённый звук и источники. Новый проект очищает документ и Undo после успешной публикации, а не до неё.

`AudioRuntimeDurableEdits` удерживает ограниченный журнал подтверждённых host controls и снимки изменений Sampler/Slicer. Откат транзакции восстанавливает также источник, управляющие значения и исходную очередь событий. Старый `clearSessionNodes` удалён; освобождение узлов проходит через публикацию сессии. Один `AudioRuntime` используется устройством, offline worker и явно обозначенными тестовыми владельцами; альтернативного производственного движка и переключателя локального хостинга нет.

Аудиозапись получает числовой токен клиента и подтверждённые путь/формат файла. Обычный Stop подтверждает `Stopped` после завершения writer, независимо от его внутреннего состояния `Idle`. При ошибке финализации остановленный владелец остаётся в реестре для повторной попытки. После завершения аварийного дочернего процесса endpoint проверяет заголовок именно этого WAV, восстанавливает длину полных кадров и передаёт завершённый take контроллеру. До завершения/восстановления всех записей перезапуск запрещён. Отказ восстановления не удаляет take из реестра. Простые команды недоступному движку возвращают ошибку; Qt-граница обрабатывает `AudioEndpointError`, сохраняя документ. Восстановление не запускает воспроизведение автоматически.

## Файловые задания и общий worker

`WorkerJob` переиспользуется рендером и `MediaWorker`: одна mailbox-реализация, проверка размеров/версий, progress, ограниченная отмена, прекращение дочернего процесса до удаления ресурсов. `RenderWorker` больше не содержит собственный второй цикл ожидания. Файловые задания ограничены двумя одновременно на владельца и выполняются с пониженным приоритетом относительно live audio.

Приложение и `daw_audio` устанавливают процессные службы при старте. `AudioFileReader`, `probeAudioFile`, загрузчик Sampler/клипов и анализаторы темпа/тональности, pitch, transients и Slicer используют `daw_worker`. В самом worker остаются исходные алгоритмы и нативные декодеры, поэтому рекурсивного запуска нет. Отсутствие helper даёт ошибку, без локального обхода. PCM передаётся неизменяемыми отображаемыми ресурсами, не через mailbox; большой файл декодируется блоками в дисковое хранилище. Общий слабый кэш `SampleLoader` переиспользует источники между импортом, инструментами и reader facade. Метаданные проверяются отдельным probe-заданием без полного декодирования.

Проверка `media_worker_test` сравнивает WAV/MP3/AAC/M4A PCM, число кадров, пути с кириллицей, seek/interleave, музыкальный анализ, pitch, transients и нарезку с исходными алгоритмами. Проверяются ограничение размера декодирования, отмена, повреждённый файл, падение/отсутствие helper и сохранение прежнего результата. ## Сохранение, экспорт и наблюдение за редактором

Ожидающие host edits при сохранении и захвате цепи объединяются через `overlayPendingParameters` с маркером `restoreAfterState`. Непрозрачное состояние плагина могло быть снято до применения этих событий; при открытии они должны наложиться поверх chunk. Обе стороны Dual Mono сохраняются независимо. В тесте отдельно проверяются сохранённая правая очередь до обработки и значение после первого DSP-блока. Recovery упавшего изолированного экземпляра использует только подтверждённый журнал, чтобы не повторять команду, вызвавшую сбой.

Исключённые из offline-рендера плагины (bypass или нулевая доля wet) подготавливаются как placeholders: worker не активирует их перед применением выбора экспорта. Ошибка Mini Module проверяется общей функцией до отправки задания. Регрессии обычного и изолированного экспорта подтверждают отказ повреждённого задания, сохранение готового файла и успешный повтор с явным bypass. Сам экспорт не продвигает DSP живого проекта. Новый интеграционный сценарий проверяет черновик batch, прослушивание, применение к двум каналам и один Undo через производственный процессный endpoint.

В протокол плагина v6 добавлен heartbeat GUI. Таймер Qt обновляет счётчик каждые 100 мс; он продолжает работать внутри отзывчивого вложенного цикла событий. Родитель наблюдает открытый редактор и после таймаута переводит зависший экземпляр в отдельный статус ошибки, после чего штатный service завершает helper. Пауза в наблюдении самим родителем начинает новое окно проверки, а перезапуск сбрасывает наблюдаемое поколение. Новых потоков, ожиданий аудиоколбэка и дополнительного аудиобуфера нет. Тест проверяет здоровое окно, зависание после подтверждённого открытия, завершение/перезапуск и на Windows — вложенный нативный цикл длительностью три секунды при таймауте 1,5 секунды.

Целевые `plugin_process_test`, `plugin_recovery_test`, `plugin_insert_test` прошли после этих изменений за 50,37 с. Проверка покрытия команд совместного редактирования `CheckCollaborationMutationCoverage.cmake` также прошла.

Начальная идентичность окна плагина берётся из документа, а не из ещё пустого кэша процессных показаний. Иначе проверка удалённых слотов могла закрыть только что созданный редактор до первого ответа `daw_audio`. Исправление общее для встроенных и внешних плагинов; новых ожиданий IPC при создании оболочки окна нет. В CTest добавлены отдельные проверки Graphit, Gravity и Equalizer с производственным контроллером. Диагностика замены плагина и открытия его окна в графическом бенчмарке использует снимки редактора. Удалён native save/load из самопроверки Equalizer: она работает с новым слотом одноразового тестового проекта.

При переключении A/B Equalizer повторная проверка идентичности выполняется только перед действительно изменяемыми параметрами; проверка перед окончательной активацией остаётся. Неизменённые значения больше не порождают управляющие IPC-вызовы. UI-тест EQ ожидает первый снимок и подтверждённые обновления кэша после жестов, с ограниченным сроком; проверки параметров, динамического порога, A/B и Undo сохранены.

Точное чтение после редактирования теперь публикует полученное значение и в существующую подписку показаний. Раньше завершение жеста уже подтверждало новый параметр, но немедленный refresh мог вернуть регулятор к старому кэшу до следующего poll. Обновление выполняется тем же последовательным broker, до возврата ответа, без дополнительного IPC; потребляемые очереди диагностик не затрагиваются. Регрессия endpoint проверяет серию точных чтений с немедленным чтением кэша, включая адрес с идентичностью экземпляра.

Тест быстрого выбора плагина явно инициализирует производственный контроллер перед вставкой. Проверка настроек учитывает допустимое сохранённое положение внутреннего окна: тело может находиться ниже рабочей области, но весь заголовок остаётся доступным, а размер ограничен рабочей областью. Проверены как чистый временный профиль, так и изолированная копия пользовательских настроек; исходные настройки не изменяются.

## Исправления после проверки stage в рабочем режиме

Обнаружена общая причина ложного переподключения устройства, остановки показаний и недоступности плагинов: после тишины LUFS-метр возвращает `-infinity`, а его прежний кодек разрешал лишь конечные значения и отсутствие (`NaN`). Отказ одного показания отклонял весь пакет, после чего endpoint помечал работающий аудиопроцесс отключённым. Кодек теперь различает отсутствие измерения, конечный LUFS и измеренную тишину; положительная бесконечность и неизвестные теги запрещены. Версия аудиопротокола повышена до 10 вместе с расширением общих часов.

Позиция для отрисовки читается из общей истории фактически отрендеренных DAC-блоков, с прежними алгоритмами задержки и loop. Она больше не ограничена частотой управляющего poll. Stop, seek, изменение loop и перезапуск устройства немедленно инвалидируют поколение этих данных; при остановке callback позиция ограничена последним готовым блоком. Отдельный accessor используется только для presentation position, а обычные проверки состояния транспорта не сканируют историю. Планировщик broker отдаёт наступившему poll очередь даже при непрерывном потоке управляющих запросов.

Запуск уже работающего устройства стал идемпотентным: при смене формата новое поколение уже запускало поток, а контроллер повторно вызывал PortAudio start. Смена конфигурации теперь также сохраняет состояние воспроизведения и возобновляет его после успешной настройки или возврата к прежнему устройству.

Регрессии дополнены тишиной в реальном дочернем runtime, непрерывными командами при обновлении транспорта и чтением общей presentation history между IPC-снимками. `plugin_isolation_ui_test` переведён с локального `TestRuntime` на полный путь `UI → daw_audio → daw_plugin_host`, с проверкой восстановления внешнего экземпляра и открытия встроенного EQ. Ручной `device_smoke` также использует производственный процессный контроллер и тихий граф, проверяет смену буфера, откат неверного устройства, LUFS и частоту обновления позиции. Прежние headless-прогоны не покрывали эти рабочие сценарии полностью.

После исправлений Release-сборка завершилась успешно; 18 связанных CTest прошли за 93,17 с (`.tmp/audio-live-fixes-tests.log`). Набор включает оба теста часов, codec/readout/endpoint/process, процессный контроллер, падение/восстановление плагина и девять UI-сценариев.

## Загрузка больших проектов: контроль реального продвижения

При разборе сообщения `Audio process control deadline expired` обнаружен общий предел: замена сессии последовательно создаёт плагины, восстанавливает их состояния и активирует их внутри одного управляющего запроса, а прежний дедлайн ограничивал весь запрос десятью секундами. Предоставленный для воспроизведения проект формата v11 содержит 19 треков и 48 слотов вставок. Такой объём может превысить общий срок при исправной работе отдельных плагинов; само наличие живого аудиопроцесса этого не различало.

В аудиопротоколе v11 добавлен счётчик завершённых шагов подготовки. Его увеличивает только управляющий поток после декодирования сессии, создания экземпляра, восстановления состояния, активации и подготовки публикации. `replace` и `apply` обновляют срок ожидания при изменении этого счётчика. Таймер, аудиоколбэк и GUI heartbeat не продлевают загрузку. Шаги без вложенного запроса к плагину сохраняют прежний предел без прогресса; для вложенных запросов действует ограниченное правило ниже. Другие управляющие запросы сохраняют абсолютный дедлайн. Дополнительный аудиобуфер или поток для этого не создаётся.

Внутри подготовки учитывается иерархия процессов: внешний watchdog не должен опередить десятисекундный таймаут самого плагина. Только фактически отправленный RPC плагина объявляет ограниченный срок ожидания с запасом на завершение дочернего процесса (5 с) и короткое штатное закрытие (100 мс). Родитель сам ограничивает этот срок 15,1 с; повторные опросы той же зависшей операции его не обновляют. Полученный ответ отмечает реальный прогресс, а RAII-наблюдатель действует лишь в управляющем потоке `replace/apply`. Тесты проверяют зависшее восстановление состояния с сохранением прежней сессии и зависшую активацию необязательного плагина с сохранением исправного соседа.

В `audio_runtime_process_test` добавлен сценарий шести CLAP-состояний, каждое из которых загружается за 300 мс: суммарная подготовка превышает установленный тестом срок 1,5 с, но завершённые шаги должны позволить публикацию. Та же проверка выполняется для добавления следующей партии через `apply`; прежняя проверка остановки неотвечающего дочернего процесса сохранена. Для проверки реальных старых проектов `engine_controller_process_test --open-project <папка>` использует производственный endpoint и существующий реестр плагинов, не открывая устройство и не сохраняя проект. Аргумент `@<файл>` читает путь в UTF-8 и устраняет зависимость от ANSI-кодировки Windows; диагностика выводит загруженные, ошибочные и недоступные слоты.

## Массовые уведомления параметров внешних плагинов

UADx Pultec при восстановлении состояния сообщает значения 2092 параметров. Прежняя очередь на 2048 уведомлений считала этот корректный пакет ошибкой протокола и выключала экземпляр. Значения редактора теперь объединяются в заранее выделенном массиве последних значений по индексу параметра и порциями передаются через существующий ограниченный канал. Публикация продолжает обход с сохранённого индекса; callback не выделяет память и не ждёт освобождения очереди. События DSP с временными метками используют прежний отдельный канал.

Начало и конец жестов сохраняют порядок в очереди. Конец жеста удерживает именно его последнее значение, даже если до публикации уже начался следующий жест того же параметра. Регрессии проверяют 4096 параметров, последовательные смены пресетов при заполненном канале и два быстрых VST3-жеста одного параметра. Некорректный индекс, нечисловое значение и переполнение очереди жестов по-прежнему дают явный отказ.

Диагностика неудачного создания различает отсутствующий класс внутри существующего файла плагина. В проверенном старом проекте сохранён UID Auto-Key 1, а установленный файл содержит Auto-Key 2 с другим UID. Такая версия не подменяется автоматически: слот и сохранённые данные остаются в проекте, сообщение перечисляет доступные классы. Реестр и оригинал проекта при диагностике не изменяются.

Проверяемая здесь платформа — Windows x64, тестовые CLAP/VST3/VST1/2. AU/macOS, коммерческие редакторы и подписанный установочный пакет требуют отдельного прогона на соответствующей системе. Исторические прогоны выше содержат эпизодические срывы дедлайна: повторный успешный запуск не считается доказательством их устранения.

Контрольные вызовы загрузки/сохранения/активации имеют ограниченные таймауты, но могут ожидаться вызывающим UI-кодом. Watchdog открытого редактора проверен на Windows, включая отзывчивый вложенный цикл событий; поведение конкретных коммерческих диалогов авторизации требует проверки с их плагинами. `Sleep`/`Tail` остаются `Continue`, пока нет надёжного пробуждения от фонового таймера плагина. Изоляция не обещает нулевые накладные расходы или отсутствие ошибок при любой аппаратной нагрузке.
