# Архитектура DAW

**Статус:** черновик v0.1
**Лицензия проекта:** GPLv3
**Целевые платформы:** Windows 10+, macOS 12+
**Язык:** C++20, UI — Qt 6.7+

> Рабочее имя проекта в коде — `daw` (неймспейс), таргеты `daw_engine` / `daw_app`.
> Переименовать одним движением до первого коммита логики.

---

## 1. Цели и не-цели

### Цели

- Многодорожечная запись и редактирование аудио и MIDI.
- Хостинг плагинов CLAP, VST3, legacy VST1/VST2 и AU, с перспективой
  изоляции в отдельном процессе.
- Сэмпл-точная автоматизация и сэмпл-точный MIDI.
- Детерминированный оффлайн-рендер: один и тот же проект даёт бит-в-бит одинаковый файл.
- Работоспособность на буфере 128 сэмплов @ 48 кГц на проекте из 50+ дорожек.

### Не-цели (сознательно откладываем)

- Нотная запись, видео-дорожка, surround/Atmos, сетевое сотрудничество.
- Собственный формат плагинов.
- Поддержка Linux, AU, LV2 — архитектурно не мешаем, но не реализуем.

### Целевой бюджет реального времени

При 48 кГц и буфере 128 сэмплов на один callback есть **2.67 мс**. Ориентир —
занимать не более 70% (≈1.9 мс), остальное запас на джиттер планировщика ОС.

Проект под GPLv3, поэтому:

| Компонент | Лицензия | Годится |
|---|---|---|
| Qt 6 | LGPLv3 | да, при динамической линковке |
| VST3 SDK | GPLv3 / проприетарная Steinberg | да, по GPLv3-ветке |
| FST 0.177.0 (`aeffect.h`/`aeffectx.h`) | GPLv3+ | да; clean-room ABI legacy VST |
| CLAP SDK | MIT | да |
| RtAudio, RtMidi | MIT-подобная | да |
| libsndfile | LGPL 2.1 | да, динамически |
| libsamplerate | BSD-2 | да |
| Tracktion Engine | GPLv3 / коммерческая | можно читать и заимствовать по GPLv3 |
| Ardour | GPLv2+ | **несовместимо с GPLv3-only** — читать можно, копировать код нельзя |

**Правило:** любой заимствованный фрагмент кода фиксируем в `THIRD_PARTY.md` с
указанием источника и лицензии в момент заимствования, а не потом.

**Отдельно про распространение:**

- **Mac App Store отпадает** — его условия конфликтуют с GPL. Распространяем
  подписанный и нотаризованный `.dmg` напрямую.
- **ASIO на Windows отпадает тоже.** Лицензия Steinberg на ASIO SDK
  несовместима с GPLv3, поэтому официальные сборки идут на WASAPI.
  Подробности и обходные пути: [docs/BUILD_ASIO.md](docs/BUILD_ASIO.md).
  Практическое следствие: WASAPI Exclusive даёт 5–12 мс round-trip, чего
  хватает для записи и сведения, но на буфере 64 сэмпла ASIO пока выигрывает.
  К M3 стоит рассмотреть собственный WASAPI-backend вместо RtAudio.

единственная гарантия, что движок можно тестировать оффлайн и что в аудио-поток
не заползёт `QObject` с его аллокациями.

## 4. Модель потоков

```
┌──────────────────────────────────────────────────────────────────┐
│ UI-поток (Qt main)                                               │
│  • владеет моделью проекта (единственный, кто её меняет)          │
│  • компилирует граф, публикует снапшоты                          │
│  • открывает окна плагинов (на macOS — обязательно здесь)         │
└───────┬──────────────────────────────────────────▲───────────────┘
        │ CommandQueue (SPSC, lock-free)           │ EventQueue (SPSC)
        ▼                                          │
┌──────────────────────────────────────────────────┴───────────────┐
│ Аудио-поток (callback драйвера, наивысший приоритет)             │
│  • обходит граф, вызывает process() узлов                        │
│  • никаких аллокаций, локов, файлов, исключений                  │
└───┬──────────────────────────────────▲───────────────────────────┘
    │ запросы на подкачку               │ готовые сэмплы
    ▼                                   │
┌───────────────────────────────────────┴──────────────────────────┐
│ Диск-поток (высокий приоритет, но ниже аудио)                    │
│  • упреждающее чтение в кольцевые буферы                         │
│  • запись входов при записи                                      │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│ Пул воркеров (обычный приоритет)                                 │
│  • построение волновых форм, сканирование плагинов               │
│  • оффлайн-рендер, freeze, конвертация                           │
│  • GC: освобождение старых снапшотов графа                       │
└──────────────────────────────────────────────────────────────────┘
```

### 4.1. Правила аудио-потока

Внутри `process()` **запрещено**:

- `new`/`delete`/`malloc`, любые контейнеры, которые могут перевыделиться;
- мьютексы, condition variables, `std::shared_ptr` с копированием счётчика по
  нетривиальному пути;
- файловый и сетевой ввод-вывод, логирование через обычные средства;
- `throw`, RTTI-`dynamic_cast` в горячем пути;
- вызовы чего угодно из Qt;
- вызовы, которые могут заблокироваться на неограниченное время.

**Как это проверяем, а не надеемся:** в debug-сборке подменяем глобальные
`operator new/delete` — если они вызваны в потоке с установленным
thread-local флагом `is_audio_thread`, немедленный `std::abort()`. Плюс
проверка на вход в мьютекс через обёртку. Один раз настроить — годы спокойствия.

### 4.2. Приоритеты и «денормалы»

- Аудио-поток поднимаем в реалтайм-класс (Windows: `AvSetMmThreadCharacteristics`
  с задачей `"Pro Audio"`; macOS: `thread_policy_set` с
  `THREAD_TIME_CONSTRAINT_POLICY`).
- В начале callback включаем FTZ/DAZ (`_MM_SET_FLUSH_ZERO_MODE`,
  `_MM_SET_DENORMALS_ZERO_MODE`), в конце восстанавливаем. Денормалы в хвостах
  ревербераций и фильтров дают падение производительности в десятки раз.
- На Apple Silicon FTZ ставится через `FPCR`, отдельная реализация.

## 5. Механика обмена между потоками

Три разных механизма для трёх разных задач. Не пытаться обойтись одним.

### 5.1. Команды UI → аудио (SPSC lock-free FIFO)

Для дискретных событий: старт/стоп, перемотка, mute/solo, подмена графа.

```cpp
// engine/include/daw/rt/command.h
struct RtCommand {
    enum class Type : uint16_t {
        Transport, SetGraph, SetParam, NoteOn, NoteOff, Locate, /*...*/
    };
    Type     type;
    uint16_t targetId;
    int64_t  timeStamp;   // позиция в сэмплах, -1 = как можно скорее
    union { float f; int64_t i; void* p; } arg;
};
static_assert(std::is_trivially_copyable_v<RtCommand>);
```

Очередь — кольцевой буфер фиксированного размера (например, 4096 команд) с
двумя атомарными индексами. Producer — UI-поток, consumer — аудио-поток.
Переполнение — это баг, а не штатная ситуация: логируем и роняем в debug.

### 5.2. События аудио → UI (SPSC FIFO обратно)

Позиция транспорта, изменение состояния, запросы на перестроение графа от
плагинов, ошибки. UI вычитывает по таймеру 60 Гц.

Показания метров через очередь **не гоняем** — это `std::atomic<float>` на
канал, UI просто читает их с той же частотой. Потеря промежуточных значений
неважна, важна свежесть.

### 5.3. Подмена графа (RCU + отложенное освобождение)

Самая тонкая часть. Граф — большая иммутабельная структура; пересобирается на
UI-потоке при любом структурном изменении (добавили дорожку, вставили плагин,
переключили роутинг).

```cpp
// Публикация нового графа
void Engine::publishGraph(std::unique_ptr<ProcessGraph> fresh) {
    ProcessGraph* old = liveGraph_.exchange(fresh.release(),
                                            std::memory_order_acq_rel);
    if (old) retireQueue_.push(old);   // GC-поток заберёт позже
}

// В аудио-потоке
void Engine::audioCallback(AudioBuffer& io, int nFrames) {
    graphEpoch_.store(++epoch_, std::memory_order_release);
    ProcessGraph* g = liveGraph_.load(std::memory_order_acquire);
    if (g) g->process(io, nFrames);
    graphEpoch_.store(epoch_ | kIdleBit, std::memory_order_release);
}
```

GC-поток освобождает отставленный граф только после того, как убедился, что
аудио-поток начал как минимум два новых цикла после подмены (счётчик эпох).
Это дешёвый аналог hazard pointers, которого здесь достаточно.

**Важно:** пересборка графа не должна прерывать звук. Узлы (в том числе
инстансы плагинов) переиспользуются между снапшотами — меняется только описание
связей и порядок обхода. Плагин создаётся/уничтожается на UI-потоке, а его
`process` вызывается только из графа, где он присутствует.

### 5.4. Параметры (атомики + сглаживание)

Крутилки, фейдеры, панорама. UI пишет `std::atomic<float>`, аудио-поток читает
и прогоняет через одно-полюсный сглаживатель (~10 мс), чтобы не было щелчков.
Для сэмпл-точности при автоматизации — см. §9.

## 6. Тайм-модель

Три представления времени, конверсии между ними — через единственный объект
`TempoMap`. Здесь ошибка обойдётся дороже всего: она проявится через полгода
на проекте с ускорениями темпа, и переделывать придётся всё.

```cpp
using SampleCount = int64_t;   // абсолютная позиция/длительность в сэмплах
using Tick        = int64_t;   // музыкальное время, целое
using Seconds     = double;    // только для UI и метаданных

constexpr Tick kTicksPerQuarter = 15360;
```

Почему 15360: делится на 2, 3, 4, 5, 6, 8, 12, 16, 32, 64 и на триоли/квинтоли
любой разумной глубины. 960 (стандарт MIDI) недостаточно для 128-х триолей и
для точного свинга.

### 6.1. Карта темпа

Кусочно-заданная функция: последовательность сегментов, каждый — либо постоянный
темп, либо линейная рампа между двумя значениями.

```cpp
struct TempoSegment {
    Tick        startTick;
    double      bpmStart;
    double      bpmEnd;      // == bpmStart для постоянного темпа
    SampleCount startSample; // кэш: пересчитывается при правке карты
};

class TempoMap {
public:
    SampleCount tickToSample(Tick) const;
    Tick        sampleToTick(SampleCount) const;
    // такты/доли для линейки и сетки
    BarBeat     tickToBarBeat(Tick) const;
    Tick        snap(Tick, GridResolution, SnapMode) const;
};
```

Для рампы позиция интегрируется аналитически (интеграл от 1/bpm(t)), не
численно. `startSample` каждого сегмента кэшируется, поэтому конверсия — это
бинарный поиск по сегментам плюс арифметика: O(log n), пригодно даже для
аудио-потока.

### 6.2. Дорожки: musical vs linear

Каждая дорожка имеет режим привязки:

- **musical** — позиции клипов хранятся в тиках, при смене темпа едут;
- **linear** — позиции в сэмплах, к темпу не привязаны (диалоги, звук к видео).

Решение принимается на уровне дорожки и хранится в проекте.

## 7. Аудио-граф

### 7.1. Узлы и порты

```cpp
class ProcessNode {
public:
    virtual ~ProcessNode() = default;

    // Вызывается ТОЛЬКО из аудио-потока. RT-safe.
    virtual void process(ProcessContext& ctx) noexcept = 0;

    // Вызывается на UI-потоке, когда граф не активен для этого узла.
    virtual void prepare(double sampleRate, int maxBlockSize) = 0;
    virtual void reset() noexcept = 0;

    virtual int  latencySamples() const noexcept { return 0; }
    virtual int  tailSamples()    const noexcept { return 0; }
};

struct ProcessContext {
    AudioBufferView   audio;      // указатели на буферы из пула
    MidiEventList     midiIn;
    MidiEventList&    midiOut;
    SampleCount       playPosition;
    int               numFrames;
    const TransportState& transport;
    ParameterView     automation; // сэмпл-точные точки на этот блок
};
```

Типы узлов: источник дорожки (стриминг с диска), MIDI-инструмент, эффект,
суммирующая шина, посыл, линия задержки (PDC), выход в устройство, метр.

### 7.2. Компиляция графа

Происходит на UI-потоке, результат иммутабелен:

1. Проверка на циклы. Разрешённое исключение — сайдчейн, он допускает цикл,
   но разрывается вставкой задержки на один блок.
2. Топологическая сортировка → линейный список операций.
3. Расчёт PDC (§7.3), вставка узлов задержки.
4. Назначение буферов из пула (раскраска графа — переиспользуем буферы там,
   где времена жизни не пересекаются; это заметно экономит кэш).
5. Разбиение на параллельные «волны» для многопоточного обхода (см. §7.4).

### 7.3. Компенсация задержки плагинов (PDC)

Алгоритм:

```
для каждого узла N в топологическом порядке:
    latency(N) = max(latency(вход) для всех входов) + собственная latency(N)

для каждого узла N:
    для каждого входа I:
        нужная задержка = max(latency(входов N)) - latency(I)
        если > 0 → вставить DelayNode
```

Тонкости:

- Плагины **меняют** латентность на ходу (переключение режима линейной фазы у
  эквалайзера, изменение lookahead у компрессора). CLAP и VST3 умеют сообщать
  об этом. Обработчик уведомления **не** пересобирает граф в аудио-потоке — он
  ставит событие в очередь к UI, тот пересобирает и публикует новый снапшот.
- Дорожки в режиме мониторинга живого входа исключаются из PDC, иначе
  исполнитель услышит себя с задержкой в полсекунды. Вместо этого их
  латентность вычитается из общей — это классическое поведение «low latency
  monitoring».
- Freeze/bounce должны учитывать PDC, иначе результат съедет.

### 7.4. Многопоточная обработка

Аудио-поток — не единственный, кто считает DSP. Граф разбивается на уровни;
узлы одного уровня независимы и раздаются пулу RT-воркеров (по числу
физических ядер минус один).

- Воркеры создаются один раз при старте, поднимаются в тот же RT-класс.
- Синхронизация — атомарные счётчики зависимостей и **спин-ожидание с
  `_mm_pause()`**, не condition variable: пробуждение через ядро стоит десятки
  микросекунд, это неприемлемо.
- Включаем начиная с M3. До этого — однопоточный обход, чтобы не отлаживать
  две сложности сразу.

## 8. Дисковый стриминг

Без него проект на 60 дорожек не поедет — 60 стерео-дорожек 24 бит/48 кГц это
17 МБ/с и десятки тысяч seek'ов.

### Схема

- На каждый **проигрываемый регион** — кольцевой буфер на 2–4 секунды.
- Диск-поток обслуживает очередь запросов с приоритетом по «сколько осталось до
  опустошения». Самый голодный буфер обслуживается первым.
- **Первые ~250 мс каждого клипа постоянно держим в RAM.** Это ключевой трюк:
  при перемотке или запуске с произвольной точки звук идёт из RAM, пока диск
  догоняет. Без этого каждая перемотка даёт слышимый провал.
- При перемотке буферы инвалидируются, читается новый участок; при этом
  транспорт не ждёт диск — играет тишину не более одного блока и логирует
  «dropout», чтобы это было видно в статистике, а не молча.

### Пик-файлы (волновые формы)

Рисовать волну из исходного файла нельзя. Для каждого аудиофайла в фоне
строится пирамида min/max:

- уровень 0: пары (min, max) на каждые 256 сэмплов;
- каждый следующий уровень — вдвое грубее;
- храним в `Peak Files/<hash>.peak`, формат — заголовок + сырые int16 пары.

UI при отрисовке выбирает уровень по текущему зуму. Один экран таймлайна — это
чтение нескольких килобайт, а не мегабайт.

## 9. Автоматизация

Автоматизация обязана быть **сэмпл-точной**. Применять значение раз в блок —
значит получить ступеньки на слышимых частотах при быстрых движениях.

```cpp
struct AutomationPoint {
    Tick   time;
    double value;          // нормализованное 0..1
    CurveType curve;       // Linear, Hold, Bezier, Exponential
    double tension;        // для безье
};
```

На каждый блок обработки компилируется список изменений с offset'ом внутри
блока:

```cpp
struct ParamChange { int frameOffset; uint32_t paramId; float value; };
```

Узел получает их через `ProcessContext::automation` и обязан обработать блок
по кускам между изменениями (так же, как обрабатываются MIDI-события).
Для плагинов CLAP это ложится один-в-один на `clap_event_param_value`, для
VST3 — на `IParameterChanges` с точками.

Режимы записи автоматизации: Read, Touch, Latch, Write, Trim.

## 10. Микшер

- **Канал:** вход → инсерты (цепочка плагинов) → фейдер → панорама → посылы →
  выход на шину.
- **Шины:** произвольная вложенность, проверка на циклы при компиляции графа.
- **Посылы:** pre/post fader, с собственным уровнем.
- **Сайдчейн:** дополнительный вход у узла плагина; разрешаем цикл ценой
  задержки в один блок, это стандартное поведение.
- **Метры:** peak, RMS, а также опциональные True Peak и LUFS (интегрированный,
  краткосрочный, моментальный) для мастера. Считаются в аудио-потоке, пишутся в
  атомики.
- **Внутренний формат:** всегда `float` 32 бита, деинтерливед (планарный).
  Планарный формат важен для SIMD и для того, чтобы не копировать при
  маршрутизации.
- Никакого клиппинга внутри цепи — float имеет запас; ограничение только на
  выходе в устройство и при экспорте в целочисленные форматы.

## 11. Модель проекта и undo

### Иерархия

```
Session
├── TempoMap, TimeSignatureMap, Markers, LoopRange
├── Tracks[]
│   ├── тип: Audio | MIDI | Bus | Folder
│   ├── Clips[]        (ссылка на Source + границы + фейды + gain)
│   ├── Automation[]   (по параметрам)
│   └── ChannelStrip   (плагины, фейдер, посылы)
├── Sources[]          (аудиофайлы и MIDI-последовательности, разделяемые)
├── Mixer              (шины, роутинг, мастер)
└── Metadata           (имя, автор, sample rate, ревизия формата)
```

Клип **не владеет** аудиоданными — он ссылается на `Source` и хранит окно
(offset, length) внутри него. Это делает split/duplicate мгновенными и
бесплатными по памяти.

### Undo/redo

Command pattern. Каждое изменение модели проходит только через команду:

```cpp
class Command {
public:
    virtual void redo(Session&) = 0;
    virtual void undo(Session&) = 0;
    virtual bool coalesceWith(const Command& next) { return false; }
    virtual std::string_view name() const = 0;   // для меню «Отменить: …»
};
```

- `coalesceWith` склеивает поток мелких изменений при перетаскивании клипа
  в одну запись истории — иначе история забьётся мусором.
- Деструктивные операции (нормализация, реверс) не правят исходник: создают
  новый `Source`, старый остаётся в проекте до очистки.
- Undo-стек не сериализуется. Ограничение — по памяти, не по числу шагов.

## 12. Хостинг плагинов

### 12.1. Порядок реализации

1. **CLAP** — MIT, API спроектирован под потокобезопасность и сэмпл-точность,
   документация внятная. Реализуется быстрее и служит эталонной абстракцией.
2. **VST3** — по GPLv3-ветке SDK. Сложнее: COM-подобная модель, шины, отдельная
   модель параметров, `IPlugView` для GUI.
3. **Legacy VST1/VST2** — отдельный AEffect-адаптер на vendored clean-room
   заголовках FST. Поддерживаются только нативные 64-битные DLL/bundles;
   каналы представлены одной плоской основной шиной, без 32-битного bridge и
   без импорта `.fxp`/`.fxb`.

Внутренний интерфейс `PluginInstance` проектируется **под CLAP**; VST3 и
legacy AEffect подгоняются под него адаптерами — не наоборот. CLAP — более
общая модель.

### 12.2. Потоковая дисциплина

- Создание/уничтожение, загрузка стейта, показ окна — только UI-поток.
- `process()` — только аудио-поток.
- Плагин может запросить перестроение (латентность, число портов) — это
  событие в очередь к UI.
- Окно плагина: на Windows встраиваем HWND, на macOS — NSView. В Qt через
  `QWindow::fromWinId()` + `QWidget::createWindowContainer()`. На macOS вызовы
  строго с main thread, иначе AppKit падает.

### 12.3. Сканирование и изоляция

- Сканирование — в **отдельном процессе**. Кривой плагин обязан ронять сканер,
  а не DAW. Результат — кэш `plugins.db` (SQLite или простой бинарник) с
  путями, ID, версиями, mtime.
- Полная работа плагина out-of-process (как в Bitwig) — цель на потом, но
  абстракцию `PluginInstance` держим такой, чтобы под неё можно было подложить
  IPC-реализацию без переписывания хоста. Конкретно: никаких сырых указателей
  на внутренности плагина наружу, весь обмен — через буферы и списки событий.

## 13. Запись

- **Round-trip latency:** записанный материал приходит с задержкой
  (вход драйвера + буфер + выход). Компенсируется сдвигом записанного региона
  назад на измеренную величину. Величину берём у драйвера и даём пользователю
  ручную поправку в сэмплах — драйверы врут.
- **Мониторинг:** три режима — off, input, auto (по состоянию транспорта).
  При direct monitoring через интерфейс DAW не участвует вовсе.
- Запись идёт в отдельные файлы через диск-поток, кольцевой буфер на входе.
  Файл дописывается инкрементально; при крэше должен остаться валидный
  фрагмент — поэтому WAV-заголовок обновляем периодически, а не только в конце.
- **Punch in/out**, предзапись (pre-roll), запись поверх с созданием
  комп-дорожек (takes) — M5.

## 14. UI-архитектура

### 14.1. Каркас

`QMainWindow` + `QDockWidget` для панелей (браузер, инспектор, микшер,
редактор). Меню, настройки, диалоги — обычные Widgets. Здесь Qt силён и
переизобретать нечего.

### 14.2. Тяжёлые виды

Таймлайн, микшер, piano roll — **`QRhiWidget`** (Qt 6.7+). Он даёт Metal на
macOS и D3D11/Vulkan на Windows единым API. `QOpenGLWidget` не берём: на macOS
OpenGL объявлен устаревшим.

Отрисовка волновых форм: из пик-пирамиды строится вершинный буфер, загружается
на GPU, обновляется только при изменении зума/скролла. Клипы — инстансированные
прямоугольники. Цель — 144 Гц на 4K при сотнях видимых клипов.

### 14.3. Как UI видит состояние движка

- **Структура проекта** живёт на UI-потоке — читается напрямую.
- **Позиция транспорта, метры, состояние** — атомики, опрашиваемые таймером
  60 Гц. Не сигналами: сигнал на каждое изменение позиции — это 375 сигналов
  в секунду на дорожку.
- Перерисовка — по одному таймеру для всего приложения, а не по таймеру на
  виджет.

### 14.4. Взаимодействие, которое нужно спроектировать заранее

Это самая недооцениваемая часть. Каждое из перечисленного — недели, не дни:

- перетаскивание клипов с привязкой к сетке, к другим клипам, к маркерам;
- инструменты редактирования (выделение, ножницы, растяжение, карандаш) и
  контекстные модификаторы;
- множественное выделение, лассо, редактирование группы клипов;
- ripple edit, режимы вставки;
- piano roll: рисование, скольжение, квантизация, velocity-лейн, легато;
- редактор автоматизации поверх клипов.

## 15. Формат проекта

Проект — это **папка-пакет**, а не один файл. Так проще резервные копии,
диффы в git и восстановление после сбоя.

```
MySong.dawproj/
├── project.json          манифест: версия формата, структура, настройки
├── Audio Files/          записанное и импортированное аудио
├── Peak Files/           кэш волновых форм (регенерируемый)
├── Plugin States/        бинарные стейты плагинов, по одному файлу на инстанс
├── Freeze Files/         результаты freeze (регенерируемые)
├── Bounces/              экспортированные миксы
└── Backups/              автосейвы: project_2026-07-27_14-32.json
```

- `project.json` — человекочитаемый JSON. Первое поле — `"formatVersion"`.
  Загрузчик обязан уметь читать все предыдущие версии; миграции — явные
  функции `migrate_v1_to_v2()`, а не «как-нибудь разберётся».
- Стейты плагинов — бинарные, отдельными файлами: они большие, и держать их
  base64 внутри JSON — путь к проектам на 200 МБ, которые открываются минуту.
- **Автосейв** каждые N минут в `Backups/` с ротацией. Сохранение — атомарное:
  пишем во временный файл, `fsync`, затем переименовываем поверх. Иначе сбой
  питания в момент сохранения уничтожит проект.
- Регенерируемые папки (`Peak Files`, `Freeze Files`) исключаются из
  «Собрать и сохранить копию».

## 16. Тестирование

| Что | Как |
|---|---|
| DSP-узлы | юнит-тесты, известный вход → известный выход |
| Детерминизм | golden-файлы: рендер тестового проекта сравнивается бит-в-бит |
| Тайм-модель | property-based: `sampleToTick(tickToSample(x)) == x` на случайных картах темпа |
| Lock-free очереди | стресс-тесты под ThreadSanitizer |
| RT-безопасность | подменённый `operator new` + abort на аудио-потоке |
| Граф и PDC | синтетические графы, проверка суммарной задержки на импульсе |
| Хост плагинов | тестовые CLAP/VST3-плагины из SDK + заведомо кривые заглушки |
| Производительность | Tracky-профиль, бенчмарк «сколько дорожек до дропаута» на CI |

**Golden-тест — главный.** Он ловит регрессии, которые слышны, но не видны:
съехавший на сэмпл PDC, изменившийся порядок суммирования, потерянное
MIDI-событие на границе блока.

## 17. Обработка ошибок

- Аудио-поток **не бросает исключений и не логирует обычным способом.** Для
  диагностики — lock-free кольцевой логгер: пишем в него POD-записи, отдельный
  поток форматирует и сбрасывает на диск.
- Потеря устройства (выдернули интерфейс) — не крэш: транспорт останавливается,
  UI показывает состояние, при возврате устройства движок переподключается.
- Дропауты считаются и показываются в статусной строке. Молчаливый дропаут —
  худший вид бага.
- Отсутствующий при загрузке плагин заменяется заглушкой, которая сохраняет
  его стейт и пропускает звук как есть. Проект не должен ломаться из-за
  переустановки системы.
- Отсутствующие аудиофайлы — диалог «найти», поиск по имени и хэшу в соседних
  папках.

## 19. Открытые вопросы

Требуют решения до соответствующего этапа, но не сейчас:

1. **Формат манифеста:** JSON читаем и диффится, но медленный на больших
   проектах. Возможен гибрид: JSON + бинарные секции для плотных данных
   (MIDI, автоматизация). Решить к M2.
2. **Модель сессии vs аранжировки.** Добавлять ли клип-лаунчер в стиле Ableton?
   Это влияет на модель транспорта (нужна вторая, квантованная временная
   шкала). Решить до M4 — потом дорого.
3. **Time-stretching:** свой алгоритм, Rubber Band (GPLv2+... проверить
   совместимость), SoundTouch (LGPL). Решить к M5.
4. **Многопоточный обход графа:** свой пул или Intel TBB. Скорее свой —
   контроль над приоритетами важнее.
5. **Скриптование:** Lua/Python для расширений. Не раньше 1.0, но публичные
   интерфейсы движка стоит держать пригодными для биндинга.

## 20. Принципы, которые не обсуждаются

1. Движок не знает про Qt. Никогда.
2. В аудио-потоке нет аллокаций, локов и файлов. Проверяется автоматически.
3. Всё время — в сэмплах и тиках, `double` секунды только для показа человеку.
4. Все события имеют offset внутри блока. Сэмпл-точность не добавляется потом.
5. Любое изменение проекта — через команду с undo.
6. Формат проекта версионирован с первого дня.
7. Дропаут — это событие, которое видно, а не тишина.
